# proposal.md — 智能日报生成器（Smart Daily Report Generator）

- 版本：v1.0
- 状态：评审中
- 关联规范：design.md、tasks.md
- 方法：SDD 六阶段工作流 · 阶段一（第 1–2 周）

## 1. 项目名称

智能日报生成器（Smart Daily Report Generator，以下简称 SDR）。

## 2. 目标（可度量）

让团队日报从成员的真实工作数据中"自动长出来"。系统通过 GitHub API 与飞书开放平台采集每个成员的提交记录、任务流转与群消息，自动生成个人日报条目，将协作成果按提交与任务的关联关系自动归属到人，由主编排模块汇总为格式统一的团队日报，经邮件与飞书机器人推送，并用 SQLite 存储日报历史。

**可度量目标（DoD）：**

- G1：系统能够接入 **≥ 2 类数据源**（GitHub 提交、飞书任务、飞书消息），每类采集器输出结构一致的 `Activity` 列表。
- G2：给定任意日期，系统能生成一份**覆盖全部 5 名成员**的团队日报，每位成员至少含一条"当日无提交/无任务"兜底条目。
- G3：协作成果（多人共同参与的一次提交/一个任务）能被**自动归属到全部相关成员名下**，归属规则可复现、可核查。
- G4：团队日报能通过**至少 2 条通道**（邮件、飞书机器人）推送，任一通道失败不影响其他通道。
- G5：每份日报落库 SQLite，支持按日期查询历史，历史可回看、可重新推送。
- G6：在**无任何外部凭证**（GitHub Token、飞书、SMTP）时，系统以 mock 数据源 + dry-run 推送降级运行，主流程仍可完整走通。

## 3. 背景

入职工程师每周的固定负担之一是"写工作日报"，其痛点在于：① 下班回忆"今天干了什么"靠记忆翻找；② 工作痕迹散落在 GitHub 提交、飞书任务、群聊消息等多个平台，逐处复制粘贴；③ 忙起来必有遗漏，写进去的是"记得住的"而非"做了的"；④ 协作成果（一起改的接口、一起修的缺陷）经常谁都没写进日报；⑤ 每人格式不一，组长还要手工汇总成团队日报。本项目通过"采集 → 生成 → 推送 → 主编排"四层结构系统性地解决这五个痛点。

## 4. 范围

### 4.1 做什么（逐条编号，供用例追溯）

- F1：GitHub 提交采集——按仓库与时间窗口拉取指定成员的 commit，输出提交信息、时间、作者。
- F2：飞书任务采集——采集指定成员在飞书任务中的任务流转（创建/完成/评论）。
- F3：飞书消息采集——采集指定成员在群聊中的有效发言（问题、结论、协作约定）。
- F4：日报生成——按成员聚合当天活动，生成个人条目；协作成果按"同一 commit/任务涉及多作者"自动归属多人。
- F5：邮件推送——将团队日报以邮件正文发送到配置的收件人。
- F6：飞书机器人推送——将团队日报通过飞书自定义机器人 Webhook 推送。
- F7：主编排——一个 CLI 入口串联"采集 → 生成 → 推送 → 落库"全流程，支持指定日期。
- F8：历史存储——SQLite 保存每份日报的内容、推送通道与生成时间，支持查询与重推。

### 4.2 不做什么（本期明确排除，逐条给出理由）

- N1：**AI 智能摘要**——本期日报为"事实聚合"，不做语义摘要与润色；语义化摘要依赖大模型，接口与评审成本高，留待 v1.1。
- N2：**Web 界面**——本期为 CLI 工具，配置与查看走命令行与文件；Web 界面涉及前端框架与鉴权，超出阶段一范围。
- N3：**考勤数据采集**——飞书考勤需额外开放平台权限且与"日报"弱相关，留待 v1.1（对应教材第 7.5 节迭代场景）。
- N4：**移动端 / 小程序**——同上，非核心诉求。
- N5：**多租户与权限体系**——本期为单团队内部工具，不做组织级多团队隔离与细粒度 RBAC。

## 5. 技术约束

- C1：语言 Python 3.12+，包管理用 uv。
- C2：数据库 SQLite（标准库 `sqlite3`），单机本地文件，无需独立服务。
- C3：HTTP 客户端统一使用 httpx（见 design.md ADR-001）。
- C4：所有凭证（GitHub Token、飞书 app_id/app_secret、SMTP 授权码）一律通过环境变量注入，**严禁写入代码或提交到仓库**。
- C5：运行形态为单机 CLI，入口 `python -m daily_report.main`。
- C6：数据源必须可替换——采集器与推送器都定义接口契约，凭证缺失时降级为 mock / dry-run。

## 6. 成功标准（功能验收 + 性能验收 + 边界场景）

### 6.1 功能验收

- S1：`python -m daily_report.main --date 2026-11-11 --mock` 能端到端生成一份含 5 名成员条目的团队日报，并落库。
- S2：任意一名成员当天无任何活动时，其条目明确显示"今日无提交/无任务"而非缺失。
- S3：构造一个两人共同参与的 commit，日报中两人的条目**都**包含该提交。
- S4：mock 模式下邮件与飞书推送均以 dry-run 输出推送内容，日志标注"未真实发送"。

### 6.2 性能验收

- S5：mock 模式下单次"采集 → 生成 → 推送 → 落库"全流程 **≤ 30 秒**。
- S6：GitHub 采集仅使用只读接口（Token 只勾选 `repo` 只读 / `read:user` 权限），单成员单仓库单次采集 commit 数上限 100 条。

### 6.3 边界场景

- S7：GitHub Token 未配置 → GitHub 采集器自动切 mock，不影响飞书与生成流程。
- S8：SMTP 未配置 → 邮件推送 dry-run，其他通道照常执行。
- S9：某采集器抛异常 → 记日志、返回空列表，**不中断**主编排（单数据源故障隔离）。
- S10：同一日期重复运行 → 生成内容幂等，SQLite 中同日期仅保留最新一份（upsert）。

## 7. 术语定义

| 术语 | 定义 |
|------|------|
| 活动（Activity） | 一次可归属到成员的工作痕迹：一次 commit、一条任务流转或一条群消息 |
| 条目（Entry） | 某成员在某个日期下聚合得到的一组活动描述 |
| 协作成果归属 | 将涉及多人的一次活动同时计入全部参与者条目的规则 |
| 采集器（Collector） | 实现 `collect(since, until) -> list[Activity]` 接口的数据源适配器 |
| 推送器（Pusher） | 实现 `push(report, date) -> bool` 接口的推送通道适配器 |
| 主编排（Orchestrator） | 串联采集、生成、推送、落库的 CLI 主流程 |
| dry-run | 不真实发送、仅打印待发送内容的降级运行方式 |
